# ADR-0003: Process hosting and the service–UI channel

- **Status:** **Accepted 2026-09-12** (ST-004 merged). Status line updated 2026-09-15.
- **Date:** 2026-09-12
- **Deciders:** project owner; build agent

## Context

Guide §2 and ST-004 describe a per-user background **capture service** and a separate **WPF UI** joined by a named pipe, with per-session tokens, so the UI can crash and restart without losing a recording. Two facts learned in ST-001 shape how that has to be built:

1. **Anything that hooks input or captures the screen must run inside the signed-in user's desktop session.** A Windows Service runs in session 0, which has no interactive desktop: low-level hooks never fire, UI Automation sees nothing, screen captures come back empty. The self-hosted runner had to be set up the same way for the same reason.
2. **Only the technician's own processes should be able to drive capture.** INV-3 and INV-4 assume that a `start`/`stop`/`discard` comes from the ScreenTail UI the technician can see, not from any process that happens to run as them.

## Decision

### Hosting

- **`ScreenTail.Service.exe` is a per-user background process, not a Windows Service.** It starts at sign-in from the user's Run key (`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, written by the installer in ST-112 and by `LoginStartup` until then) and runs for the whole session, windowless. It owns hooks, capture, redaction, the store and the outbox.
- **`ScreenTail.UI.exe` runs on demand** (tray, HUD, Review, Settings) or at sign-in when the user chooses "Start UI at login". It holds no capture state; it is a view over the service.
- Exactly one service per user: it takes a named mutex `ScreenTail.Service.<user-sid>` and exits if it already exists.

### Channel

- **Named pipe `ScreenTail.<user-sid>`**, server in the service, one instance per connected client. On Windows the pipe ACL admits only the owning user (and no network access). .NET's pipe API is cross-platform, so the transport and its tests run on the macOS dev box (where it is a Unix socket).
- **Framing:** 4-byte little-endian length prefix + UTF-8 JSON, one message per frame, 1 MiB maximum. Messages are `type`-discriminated records generated by hand in `ScreenTail.Shared/Ipc` (System.Text.Json polymorphism, unknown members rejected), the same style as the session schema. Contract version is `IpcContract.Version`.
- **Direction:** commands UI → service (`hello`, answered by `hello_ack`; then `start`, `pause`, `resume`, `stop`, `discard`, `mark_moment`, `get_state`, each answered by a `result`); events service → UI (`hello_ack`, `state_changed`, `rejected`). Every connected, authenticated client receives every event, so a tray, a HUD and a Review window can all be open at once.

### Authentication (per Guide §5, "every command is authenticated with the session token")

A connection must pass three checks before its first command is accepted; failing any one gets a `rejected` reply, an audit row (`ipc_rejected_<reason>`, nothing else), and a closed pipe.

1. **Same user.** The pipe ACL on Windows; the socket's file permissions elsewhere.
2. **Verified client executable.** The service resolves the client's process from the pipe and checks its executable. Release builds: Authenticode-signed by the same publisher certificate as the service itself. Unsigned (development) builds: the client executable must sit in the same directory as the service executable. This is `IClientVerifier`; the Windows implementation lives in the service, tests use fakes. It is what makes ST-004's "unsigned process is rejected" true.
3. **Service-run token.** The service generates a random 32-byte token at start and writes it to `%LOCALAPPDATA%\ScreenTail\ipc.token` (user-only ACL). The UI reads it and sends it in `hello`; the service compares in constant time. The token rotates every time the service starts, so a stale UI cannot act on a new service run by accident.

The token does not defend against another process running as the same user reading the file; the executable check does. The token exists so that the *channel* is authenticated per service run and so that a bug that skipped the executable check would still not accept arbitrary connections.

### Reattach

The service keeps all session state. A client that disconnects for any reason is forgotten; a client that connects gets the current state in `hello_ack`. The UI reconnects with backoff (100 ms, doubling to 2 s) and shows "Capture service not running — Start" (Spec, ST-070) when it can't. ST-004's requirement is a reattach within 2 s; the transport achieves it in milliseconds.

## Consequences

- The installer (ST-112) registers the Run key for the service and, optionally, the UI. Uninstall removes both.
- The threat model (ST-012) covers: token file confidentiality, the verifier's failure modes, and the pipe ACL. ST-012's service-binary integrity check reuses the same signature logic in the other direction (UI verifying the service), and should replace the verifier's thumbprint comparison with `WinVerifyTrust`, which validates the certificate chain and timestamp as well as the signer.
- ST-020's state machine publishes through the same `state_changed` event; `CaptureStateSnapshot` is deliberately small and grows there.
- What ST-004 leaves to later: pipe ACL hardening beyond the default user-only DACL (ST-012), the UI's connection banner (ST-070), the installer's Run key (ST-112).

## Alternatives considered

- **A real Windows Service plus a per-user helper for capture.** Two more processes and a privilege boundary for no gain: everything that matters must run in the user's session anyway, and the backend holds nothing the service would need elevated rights for.
- **gRPC or HTTP on localhost.** A listening TCP port, which ST-012 forbids in release builds, plus a heavier dependency for a handful of messages.
- **Windows-only pipe code (P/Invoke) instead of `System.IO.Pipes`.** Would move the transport tests to the laptop for no benefit; the ACL and client-process lookup are the only Windows-specific parts and are isolated behind interfaces.
